# Roadmap — 2026-06-02 (SUPERSEDED)

> **Superseded by [roadmap-2026-06-02.md](.claude/plans/roadmap-2026-06-02.md)** — the project pivoted to frontend-first phase ordering on 2026-06-02. This file is kept for history; do not act on its phase list.

Snapshot of where the project stands and the next phases, in order. Supersedes [roadmap-2026-06-01.md](.claude/plans/roadmap-2026-06-01.md), [roadmap-2026-05-29.md](.claude/plans/roadmap-2026-05-29.md), and the older [roadmap-2026-05-28.md](.claude/plans/roadmap-2026-05-28.md).

The project is **lukehirsch**: a monorepo for a personalized portfolio site **plus** the Job Application Creator (JAC) — a tool that ingests a job posting, tailors a CV + cover letter from the user's career database, stores the application, sends follow-up reminders, and creates a personalized portfolio link for the recruiter.

This roadmap is split into **what shipped since 2026-05-29**, **what's next** (the work that actually gets us to a usable product), and **deferred** (production hardening + nice-to-haves).

## What shipped since 2026-05-29

The 2026-05-29 roadmap planned Phase 2 (2FA) using `django-otp` + `django-two-factor-auth`. We chose `django-allauth[mfa]` headless mode instead — it gives us signup/login/password-reset/email-verification **and** TOTP + WebAuthn passkeys + recovery codes in one library, with a JSON-only API surface that the SPA can drive directly.

**Auth + MFA backend — mostly shipped (allauth headless)**
- `allauth`, `allauth.account`, `allauth.mfa`, `allauth.headless` in `INSTALLED_APPS`; sites framework wired.
- `AUTHENTICATION_BACKENDS` includes both `ModelBackend` (for admin login) and `allauth.account.auth_backends.AuthenticationBackend`.
- Email-as-username (`ACCOUNT_LOGIN_METHODS = {"email"}`), mandatory verification, verification-by-code enabled.
- `MFA_SUPPORTED_TYPES = ["recovery_codes", "totp", "webauthn"]` with passkey login + signup enabled. `MFA_WEBAUTHN_ALLOW_INSECURE_ORIGIN` gated on `DEBUG` for local dev.
- `HEADLESS_ONLY = True`; `_allauth/` mounted in [backend/lukehirsch/urls.py](backend/lukehirsch/urls.py); reset-password frontend URL templated against `FRONTEND_URL`.
- **Console** email backend only (real SMTP deferred to deployment phase).

**DRF foundation — laid, not wired**
- `rest_framework`, `corsheaders`, `channels`, `daphne` installed and in `INSTALLED_APPS`.
- `REST_FRAMEWORK` settings block: `SessionAuthentication` + `IsAuthenticated` defaults.
- CORS + CSRF trust the React origin via `FRONTEND_URL`.
- [backend/jac/serializers.py](backend/jac/serializers.py) — full set: `Domain`, `Location`, `Education`, `Certification`, `Skill` (with `years_of_experience` computed), `Job`, `Project`, `Language`, plus a top-level `CvSerializer`. **Uncommitted.**

**`spa` app — bootstrapped**
- [backend/spa/models.py](backend/spa/models.py) — `UserProfile` (one-to-one with `auth.User`, created automatically via `post_save` signal): identity (display_name, avatar, bio), professional contact (phone, website, linkedin_url, github_url), locale (timezone), UI prefs (theme, contrast), notification opt-ins (email_reminders).
- Migration `0001_initial.py` generated. **Uncommitted.**
- Admin registered.

**Async stack — wired in settings, not used**
- `daphne` first in `INSTALLED_APPS`; `ASGI_APPLICATION = "lukehirsch.asgi.application"`.
- `CHANNEL_LAYERS` using `channels_redis` against `REDIS_URL`; Redis `CACHES`.
- Full Celery config block (`CELERY_BROKER_URL`, result backend, serialization, time limits). **No `celery.py`, no tasks, no ASGI routing yet.**

**Database — Postgres-by-default in prod**
- `DATABASES` switches on `DEBUG`: SQLite in dev, Postgres in prod (env-configurable host/user/password/conn-age).

**CV pipeline — extended well beyond the prior plan**
- [backend/jac/cv.py](backend/jac/cv.py) gained:
  - `ai_tailor_with_fallback` — 5-rung tiered pipeline (conversational → filter → keyword → deterministic → unfiltered), each rung matched to a model capability tier; each failure restores the pre-call snapshot so partial mutations don't leak.
  - `ai_conversational_tailor` — loose prompt + selection contract for reasoning models.
  - `ai_keyword_filter` — LLM keyword extraction → deterministic match (SLM-friendly).
  - `_filter_with_floor` — `_MIN_PER_SECTION` floor so threshold filtering can't wipe a section entirely.
- [backend/jac/stopwords.py](backend/jac/stopwords.py) — multi-language stopword sets (strict + loose) used by `extract_keywords`.
- [backend/jac/llm.py](backend/jac/llm.py) gained `tailor_cv_conversationally` (with id-validation drop of hallucinated picks; raises if <2 valid survive — drives the fallback).
- New management command [backend/jac/management/commands/cv_import.py](backend/jac/management/commands/cv_import.py).

## What's NOT shipped — the gaps that actually block a usable product

The earlier roadmap focused on plumbing (auth, DRF, frontend CRUD, deployment) and treated the **JAC application loop** itself as something that would emerge from the plumbing. It won't. These are the things that have to exist for a user to do anything valuable:

1. **JAC's core models don't exist.** `JobPosting`, `Application`, `CoverLetter`, `FollowUp` — the units of value JAC is supposed to produce. Today `CV` operates on raw posting text in memory and discards it. Without persisted applications there's no follow-up tracking, no portfolio link to create, no analytics.
2. **No cover-letter generation.** `jac/llm.py` has `analyze_job` and the scoring/tailoring prompts but no cover-letter prompt wrapper or renderer.
3. **No PDF/DOCX export.** Only Markdown via `CvRender.export_md()`. The 2026-05-29 roadmap handwaved "PDF/DOCX will happen on the frontend" — but recruiters expect attachable PDFs, and there's no plan for that anywhere.
4. **No CV import.** First-run UX is "type your entire career history into Django admin." This is the single biggest onboarding blocker — every user needs to bootstrap from an existing resume.
5. **No streaming UI for tailoring.** Agentic tailoring takes 20–60s; users need progress feedback. ASGI is wired but no streaming endpoint exists.
6. **No spend caps / LLM budget UI.** `LLMRequestLog` records every call but nothing enforces a per-user cap or surfaces spend. Users can burn through their own provider budget unbidden.
7. **No portfolio link system.** `PortfolioLink`, `VisitorResponse`, public landing, personalized views, JAC→PortfolioLink auto-creation when an application is sent. The whole "personalized portfolio for the recruiter" half of the product.
8. **No real SMTP.** Currently console only. This gates: email verification (allauth needs it), password reset, follow-up reminders, application sending. Mandatory for any real use.
9. **No API docs.** `drf-spectacular` would generate OpenAPI for the SPA dev surface.
10. **Production hardening missing:** no Sentry, no DB backups, no GDPR export/delete, no rate limiting on public endpoints, no DRF pagination/filtering defaults.

The phase ordering below reorganises around closing these gaps.

### Phase D — JAC application flow models + cover-letter generation

The first phase where the user gets to **do the thing JAC is for**.

- New models in [backend/jac/models.py](backend/jac/models.py):
  - `JobPosting(user, source_url, title, company, raw_text, analysis_json, created_at)` — persisted ingested postings; `analysis_json` caches the `analyze_job` output.
  - `Application(user, job_posting, cv_snapshot_json, cover_letter_id, status, created_at, sent_at, applied_via)` — `cv_snapshot_json` is the tailored CV payload (entry ids + the analysis); `status` ∈ {`draft`, `sent`, `rejected`, `interview`, `offer`, `closed`}.
  - `CoverLetter(application, body, generated_with_alias, generated_at)`.
  - `FollowUp(application, scheduled_for, sent_at, kind, body)` — `kind` ∈ {`gentle_nudge`, `status_check`, `thank_you`}.
- New LLM wrapper `jac.llm.generate_cover_letter(job_text, analysis, cv_payload, profile, llm, user)` — single call; uses `UserProfile` for sign-off.
- API endpoints under `/api/jac/`:
  - `POST /api/jac/postings/` — body `{source_url}` or `{raw_text}`; stores the posting; kicks off analysis.
  - `POST /api/jac/postings/<id>/tailor/` — runs `ai_tailor_with_fallback` against the posting; returns CV payload (does **not** persist an Application yet).
  - `POST /api/jac/applications/` — accepts a tailored CV payload + cover-letter prompt; persists an `Application` + `CoverLetter`.
  - `GET /api/jac/applications/` — list with status filter.
- Frontend: "new application" wizard — paste posting → review analysis → review tailored CV (with override per entry) → review/edit cover letter → save as draft.

### Phase E — Async + streaming + email + follow-ups

Stand up the async stack that's already configured. First the infrastructure, then the two features that need it.

- `backend/lukehirsch/celery.py` — Celery app discovery; beat schedule.
- ASGI routing for streaming tailoring (`/ws/jac/tailor/` or HTTP SSE under `/api/jac/cv/tailor/stream/`) — emits per-tier progress events so the UI can show "trying conversational..." → "scored 38 entries" → "done".

- Per-user spend caps: `UserProfile.monthly_llm_budget_cents` (nullable = no cap); `LLMRequestLog` rolling sum vs cap before each LLM call.

## Cross-cutting principles to preserve

These are invariants the working code already holds; keep them as new phases land:

- **Per-user LLM config end-to-end.** Every LLM call in user-driven flows passes `user=` so personal `LLMConfig` rows are honoured. `settings.LLM["default"]` is the free fallback only. New endpoints and Celery tasks must continue to thread the user through.
- **All career entries are user-scoped.** Inherited from the abstract `CvEntry`. Every new model that holds user data must keep this contract.
- **API keys never leave the server.** `LLMConfig.api_key` is Fernet-encrypted; admin uses `PasswordInput`; never echoed in any serializer.
- **Career models in admin.** Every new model gets a `ModelAdmin` registration in the same app's `admin.py`.
- **Secrets via `os.getenv()`.** Never hardcoded. Insecure dev fallbacks (mirroring `SECRET_KEY`) are acceptable for `LLM_ENCRYPTION_KEY` in dev only.
- **Django ORM only.** No raw SQL.
