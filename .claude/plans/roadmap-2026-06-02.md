# Roadmap — 2026-06-02 (frontend-first revision)

Supersedes [roadmap-2026-06-01.md](.claude/plans/roadmap-2026-06-01.md), [roadmap-2026-05-29.md](.claude/plans/roadmap-2026-05-29.md), and the older [roadmap-2026-05-28.md](.claude/plans/roadmap-2026-05-28.md).

The project is **lukehirsch**: a monorepo for a personalized portfolio site **plus** the Job Application Creator (JAC) — a tool that ingests a job posting, tailors a CV + cover letter from the user's career database, stores the application, sends follow-up reminders, and creates a personalized portfolio link for the recruiter.

## Why this revision

The previous roadmap treated the SPA as Phase B, after finishing the remaining DRF wire-up and before doing the JAC application flow. That order assumes we can design the application flow without dogfooding it. We can't.

To build a working JAC tool we need first-hand experience using the tool. To get that, we need a *flawless, extended* personal CV in the system — which means a usable web UI for editing career entries — which means the frontend foundation has to come before any further JAC backend work.

This revision reorders around that insight: **frontend-first, then iterate**. Each frontend phase exposes a real backend gap; each backend phase closes that gap and unlocks the next frontend phase. Deployment happens after the SPA is locally usable but before any user-facing surface is exposed.

## Frontend stack (locked 2026-06-02)

- **TanStack Router + TanStack Query** as independent libraries — no Start framework (server is Django; SSR isn't worth a Node layer).
- **Tailwind v4 + shadcn/ui** (Radix-based copy-paste components).
- **TanStack Form** for entry editors.
- **TanStack Table** for list views.
- Vite same-origin proxy keeps cookies + CSRF simple in dev.

### Phase 3 — Backend refactors + career-data model evolution + hardening + first SPA backend

Driven by what Phase 2 surfaced, plus the career-data model gaps that block *trustworthy* CV generation, plus a pre-deployment hardening pass (Phase 5 is on the horizon).

**3a. Career-data model evolution (jac).** These feed CV generation (Phase 6) and the numbers recruiters actually read, so they land before generation is built.

- **Manual `years_of_experience` override on `Skill`.** Today `years_of_experience` is a computed property ([backend/jac/models.py](backend/jac/models.py)): the whole-year delta since the *earliest* of `first_used` / earliest related Job / earliest related Project. That over-counts intermittent skills — e.g. C/C++ reads 16 years (first language ever picked up) when actual hands-on time is ~2–3 semesters, which makes the reader assume mastery that isn't there. Add a nullable `years_of_experience_override` (`IntegerField`). The property returns the override when set, else the computed value. Automatic recognition stays the default; the override is the escape hatch for skills that step out of the ordinary. Serializer exposes both: effective `years_of_experience` (read-only) + writable `years_of_experience_override`. Editor surfaces it as "auto: N — override".
- **Skill relations.** Some skills are genuinely connected — e.g. *Accounting* (a domain skill) done *with* *SevDesk* (a tool). Add a symmetric self-referential M2M `related_skills` (`blank=True`) so the tailor pipeline can surface a cluster: a posting that mentions accounting can pull SevDesk along. Start symmetric ("these go together"); promote to a `through` model carrying a relation-type (e.g. directed "implemented-via-tool") only if that proves necessary. Picker UI: a `SkillPicker` field on the skill editor.
- **`ResumeSnippet` model (jac).** Reusable, first-person prose blurbs the user writes by hand; CV/cover-letter generation stitches the relevant ones together with minimal LLM glue between them — keeping the application's voice human instead of fully-generated "AI slop". `ResumeSnippet(user, title, content, kind, domains M2M, skills M2M, is_active, created_at, updated_at)` — `kind` ∈ `{intro, achievement, value_statement, closing, other}`; `domains`/`skills` drive relevance matching at generation time. Exposed at `/api/jac/resume-snippets/`. User-scoped + admin-registered. The Phase 6 generation wrapper selects snippets by relevance, orders them, and asks the LLM only to write connective tissue.

> CV generation note: 3a is the data groundwork resume generation rides on. The generation pipeline proper (`JobPosting`/`Application`/`CoverLetter`, `/api/jac/cv/tailor/`, PDF/DOCX) stays Phase 6, but with these prerequisites in place it can be pulled forward / interleaved if dogfooding demands it.

**3f. Output localization (German-first CV rendering).** The career DB is authored largely in English, but applications target corporate Germany, where the German wording is what a Personalleiter judges. Selection/ranking already match cross-language (the scoring prompts in [backend/jac/llm.py](backend/jac/llm.py) explicitly "match on meaning, not surface tokens"), so **only the output rendering needs a target-language variant** — the filtering pipeline is untouched. Two layers, deliberately different machinery:

- **Deterministic labels (Django i18n, no LLM).** Section headings (`Experience` → `Berufserfahrung`) and the `gettext_lazy` enums already in [backend/jac/models.py](backend/jac/models.py) (proficiency, category, fluency, job-type). Add `LocaleMiddleware` + `LOCALE_PATHS` + `de` to settings, wrap `CvRender`'s section titles in `gettext`, then `makemessages -l de` → fill `locale/de/LC_MESSAGES/django.po` → `compilemessages`. Free, consistent every run.
- **Free-text prose (LLM, stored + editable — *not* regenerated per run).** Translates `description` (every entry), job `title`, `field_of_study`, and the 3a `ResumeSnippet` prose. Decided 2026-06-09: store translations, don't re-translate on every tailor — the German audience judges the German, so it must be reviewable and hand-correctable, and re-translating wastes tokens on text that rarely changes.
  - **Storage:** `translations = JSONField(default=dict)` on the abstract `CvEntry` base → `{"de": {"description": "...", "title": "..."}}`. One `makemigrations` touching all six entry tables; one column, arbitrary target languages, no joins, fits the in-memory `CV` snapshot pattern with zero extra queries (chosen over `django-modeltranslation`'s per-language columns or a generic-FK translation table). A `tr(field, lang)` resolver on the base returns the translated value, else the source. `ResumeSnippet` gets the same field.
  - **LLM wrapper:** `translate_entries(entries, target_lang, llm, user=)` in [backend/jac/llm.py](backend/jac/llm.py) — batched, **glossary-protected** so proper nouns and tech terms pass through verbatim (skill names like `Python`/`React`, company + institution + certification names, URLs). A per-model translatable-field map drives which fields are sent; skill `name` is excluded.
  - **Target language:** detected from the posting (add `language` to `analyze_job`'s output schema), with an explicit per-generation override; threaded as `target_language` through `ai_tailor_with_fallback`. German jobs → German automatically; nothing personal-cased into the multi-user system. After selection, lazily fill only the *chosen* entries' missing `translations[lang]`, then persist.
  - **Surfacing:** `CvRender` + the jac serializers resolve text through `tr()` so both the `/api/jac/` payload and the Markdown export honour the target language; `translations` is writable so the CRUD UI (and a future Phase 7 per-entry override) can hand-fix phrasing.
  - **Tests:** i18n label rendering under `de`; glossary pass-through (tech terms + names survive untranslated); lazy-cache reuse (a second tailor for the same language issues no LLM translate call); detection → override precedence.

## Cross-cutting principles to preserve

Invariants the working code already holds; keep them as new phases land:

- **Per-user LLM config end-to-end.** Every LLM call in user-driven flows passes `user=` so personal `LLMConfig` rows are honoured. `settings.LLM["default"]` is the free fallback only. New endpoints and Celery tasks must continue to thread the user through.
- **All career entries are user-scoped.** Inherited from the abstract `CvEntry`. Every new model that holds user data must keep this contract.
- **API keys never leave the server.** `LLMConfig.api_key` is Fernet-encrypted; admin uses `PasswordInput`; never echoed in any serializer.
- **Every model in admin.** Every new model gets a `ModelAdmin` registration in the same app's `admin.py`.
- **Secrets via `os.getenv()`.** Never hardcoded. Insecure dev fallbacks (mirroring `SECRET_KEY`) are acceptable for `LLM_ENCRYPTION_KEY` in dev only.
- **Django ORM only.** No raw SQL.
