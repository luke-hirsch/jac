# Roadmap — 2026-05-29

Snapshot of where the project stands and the next phases, in order.
Supersedes [roadmap-2026-05-28.md](roadmap-2026-05-28.md).

## Phase 1 — Per-user LLM configs (shipped 2026-05-29)

This phase replaced the "operator-provided LLM" model with a "user-provided LLM" model. The previous design assumed `settings.LLM` was the single source of truth for every alias; we shipped a multi-tenant gateway where each user owns their own provider/model/API-key per alias, and `settings.LLM` shrank to a free Ollama fallback. **This is reflected throughout the CV pipeline:** every `CV` method that calls an LLM threads `user=self.user` through `jac/llm.py` into `llm_connector`, so a CV tailored for user N uses user N's configured provider — not a global default.

- Career DB models in [backend/jac/models.py](backend/jac/models.py): `Domain`, `Location`, `CvEntry` (abstract), `Education`, `Certification`, `Skill`, `Job`, `Project`, `Language`. Every entry is user-scoped.
- CV pipeline in [backend/jac/cv.py](backend/jac/cv.py) — `CV` class with `deterministic_filter`, `extract_keywords`, `ai_filter_entries`, `ai_rank_entries`, `agentic_tailor`. Scored entries get transient `.relevance_score` / `.relevance_reason`. AI methods pass `user=self.user` into the prompt wrappers so per-user configs apply end-to-end.
- LLM prompt wrappers in [backend/jac/llm.py](backend/jac/llm.py): `extract_job_keywords`, `analyze_job`, `score_entries_for_job`, `score_entries_with_analysis`. All accept `user=` and forward it to `llm_connector.complete`.
- Markdown rendering in [backend/jac/render.py](backend/jac/render.py) — `CvRender.export_md()`.
- `LLMConfig(user, alias, provider, model, url, max_tokens, api_key_encrypted, extra)` in [backend/llm_connector/models.py](backend/llm_connector/models.py). Unique on `(user, alias)`. `api_key` property Fernet-encrypts via [backend/llm_connector/crypto.py](backend/llm_connector/crypto.py).
- Resolution in [backend/llm_connector/conf.py](backend/llm_connector/conf.py): with `user`, try `LLMConfig(user, alias)` and fall back to `settings.LLM["default"]` (the zero-cost Ollama config) on miss. Without `user`, read settings directly.
- `LLMRequestLog` gained a nullable `user` FK so spend can be audited per user.
- Admin: `LLMConfigAdmin` with `PasswordInput` for api_key; never exposed in list views.
- `llm_check --user <pk>` checks a user's configured aliases (parallel) in addition to the default-only check.
- `settings.LLM` simplified to a single `default` entry — the free Ollama fallback. Paid providers live exclusively in per-user `LLMConfig` rows. `LLM_ENCRYPTION_KEY` is in [backend/lukehirsch/settings.py](backend/lukehirsch/settings.py) with an insecure dev fallback (mirrors `SECRET_KEY`).
- Admin: all career models registered in [backend/jac/admin.py](backend/jac/admin.py); `LLMConfig` and `LLMRequestLog` in [backend/llm_connector/admin.py](backend/llm_connector/admin.py).
- Tests: 130 across `jac` and `llm_connector`, all passing (`python manage.py test`).

**Working-tree note (2026-05-29 PM):** [backend/llm_connector/client.py](backend/llm_connector/client.py) has an uncommitted formatter pass (whitespace only — no behavior change). Nothing else is dirty; the init commit is the latest.

**Not yet built:** DRF endpoints (`jac/views.py` is empty, `jac/urls.py` doesn't exist, project [urls.py](backend/lukehirsch/urls.py) only routes `admin/`), Application/FollowUp models, frontend (still default Vite template), `spa` app (empty scaffold), Celery jobs, 2FA, deployment.

## Phase 2 — 2FA / multi-factor auth

- Add `django-otp` + `django-two-factor-auth` (or `django-allauth` with MFA).
- Wire into `INSTALLED_APPS` + URL config; require 2FA on the admin and the future API surface.
- Per-user TOTP setup flow in the admin first; later in the SPA.
- Tests: enrolment, verification, recovery codes.
- Why before DRF: the API will expose API-key management (LLMConfig), follow-up creation, and CV tailoring — all need a strong auth gate, not just session login.

## Phase 3 — DRF serializers + CRUD APIs

- Install DRF, add `rest_framework` to `INSTALLED_APPS`, add a `REST_FRAMEWORK` settings block (session + token auth, paginated defaults).
- New `backend/jac/serializers.py` — one serializer per career model: `Domain`, `Location`, `Education`, `Certification`, `Skill`, `Job`, `Project`, `Language`. Nested reads where it helps; PK writes.
- New `backend/jac/views.py` — `ModelViewSet` per model, filtered to `request.user`'s entries. Permission class: `IsAuthenticated` + 2FA verified.
- New `backend/jac/urls.py` — DRF `DefaultRouter` registrations.
- Also expose `LLMConfig` under `/api/llm/configs/` so the SPA can manage personal API keys without going through the admin.
- Wire into project [urls.py](backend/lukehirsch/urls.py) under `/api/jac/` and `/api/llm/`.
- Tests: list/create/retrieve/update/delete per model, plus user-scoping (one user cannot see another's entries or LLMConfigs).

## Phase 4 — Frontend CRUD

- Add `react-router-dom`, an HTTP client (axios or fetch wrapper), and TanStack Query for cache/mutation handling.
- Auth surface: login form + 2FA challenge against Django.
- One list + edit page per career model, mirroring the admin: table view, create modal, edit drawer, delete confirm.
- LLMConfig management screen: list, create, edit (API key shown only on creation, never on read).
- Keep styling minimal — this is plumbing, not the portfolio UI.

## Phase 5 — Async stack

- Add Daphne (ASGI) so we can do streaming responses and websockets later.
- Add Celery + Redis for background jobs. First job: scheduled follow-up reminders (needs an `Application` / `FollowUp` model — design it as part of this phase).
- Wire a `celery.py` into [backend/lukehirsch/](backend/lukehirsch/), beat schedule for periodic checks.
- LLM streaming endpoints exposed over ASGI (the synchronous DRF endpoints stay for CRUD).

## Phase 6 — Comment & docstring cleanup ✓ Shipped (2026-05-29)

Done out of order alongside the per-user LLM shift. Every `backend/` module now leads with a docstring describing *why* the module exists and the public contract; "what" comments have been stripped. Frontend pass deferred until Phase 4 actually adds React code worth documenting (still the default Vite template).

## Phase 7 — Deployment

- `Dockerfile` for backend (Python 3.12, Daphne entrypoint) and frontend (multi-stage: Vite build → nginx serve).
- `docker-compose.yml`: backend, frontend, postgres, redis, celery worker, celery beat, nginx reverse proxy. The existing [config/](config/) nginx config is the starting point.
- `.env.example` checked in (must include `LLM_ENCRYPTION_KEY` instructions), real `.env` mounted via compose.
- GitHub Actions:
  - `ci.yml` — lint + `python manage.py test` + `npm run build` on every PR.
  - `deploy.yml` — on push to `main`, build images, push to registry, SSH into the VPS, `docker compose pull && up -d`.
- DB migration strategy: SQLite → Postgres before first deploy.
